# 选课接口压测报告

**测试日期**：2026-09-10　**工具**：Apache JMeter 5.6.3　**环境**：本机 Docker 单机（应用 / MySQL / Redis / RabbitMQ 四个容器），JDK 17

**100 个真实学生账号同时抢一门只有 10 个名额的课，数据库始终没有超卖**：冗余计数 `selected_count`、选课记录数精确等于容量 10，其余学生全部进入候补队列。压测过程中定位出 3 个并发缺陷，均已修复。

---

## 一、测试场景

- **业务**：`POST /api/courses/select?courseId=1`，课程「Java入门」容量 10
- **账号**：`20260001`–`20260100` 共 100 个学生，各自用真实 JWT（`loadtest/tokens.csv`）
- **并发**：JMeter 100 线程 × 1 轮，`Synchronizing Timer` 让 100 个请求**同一时刻**发出（制造惊群）

| 指标 | 第 1 轮<br>原始代码 + 原始配置 | 第 2 轮<br>修复 2 个 bug | 第 3 轮<br>第 2 轮 + 调优配置 |
|---|---|---|---|
| 请求数 | 100 | 100 | 100 |
| 成功（`code=200`） | **3** | **99** | **99** |
| 失败 | 97 | 1 | 1 |

| 吞吐 TPS | 704 ⚠️ | 65.3 | 63.9 |

| P50 / P90 | 106 / 128 ms | 1078 / 1288 ms | 1154 / 1333 ms |

⚠️ **第 1 轮的 704 TPS 是无意义的虚高**：97% 的请求在 100ms 内被直接拒绝，没有做任何实际工作。这个数字恰好说明「高 TPS」本身不能证明系统好用。

## 三、不超卖验证（本报告的核心）

JMeter 报告只能反映性能，**是否超卖必须查库**。每轮压测结束、等 MQ 消费者写完候补队列后再查：

```sql
SELECT c.selected_count,
       (SELECT COUNT(*) FROM course_selection     WHERE course_id=1 AND status=0 AND deleted=0) AS rows_cnt,
       (SELECT COUNT(*) FROM course_waiting_queue WHERE course_id=1 AND deleted=0)            AS queue_cnt
  FROM course c WHERE c.id = 1;
```

| 校验项 | 第 1 轮 | 第 2 轮 | 第 3 轮 | 期望 |
|---|---|---|---|---|
| `selected_count`（冗余计数） | 3 ⚠️ | **10** | **10** | = 容量 10 |
| 选课记录数 | 3 | **10** | **10** | = 容量 10 |
| 候补队列人数 | 0 | **89** | **89** | 尽量接近 90 |
| **是否超卖** | **否** | **否** | **否** | 否 |

**结论**：第 2、3 轮中 `selected_count` 与选课记录数始终精确等于容量 10，一条不多。防超卖的最后一道防线是数据库原子扣减：

```sql
UPDATE course SET selected_count = selected_count + 1
 WHERE id = ? AND selected_count < capacity
```

`WHERE selected_count < capacity` 让「检查」和「扣减」变成一条原子 SQL，这是超卖被彻底挡住的原因。

> ⚠️ 第 1 轮库里最终有 4 条选课记录：3 条来自压测，另外 1 条是压测后为定位错误原因人工发的一次请求。

## 四、压测中发现的问题

### 4.1 已修复：Redis 锁是「抢不到就立刻放弃」

**现象**：第 1 轮 100 个请求里 97 个返回 `code=400 系统繁忙，请稍后重试`，候补队列 0 人。

**原因**：`RedisLockUtil.tryLock` 早期实现就是一次 `SETNX`，抢不到立刻返回 `false`，没有任何重试：

```java
return redisTemplate.opsForValue().setIfAbsent(key, value, timeout);   // 一次定生死
```

调用方传的 `Duration.ofSeconds(3)` 实际是**锁的过期时间**，不是等待时间（注释写的「最多等待3秒」是错的）。于是第 1 个人拿锁去处理，剩下 99 个人试一次没抢到就全部走人——等锁放开时人已经走光了。

**影响**：0 超卖，但功能不可用——高并发下 97% 的学生既没选上课、也没进候补。

**修复**：`tryLock` 改为自旋重试（首次 10ms、指数退避至 50ms 上限），到 `waitTime` 用尽才返回失败；并把「等待时间」和「过期时间」拆成两个独立参数：`tryLock(key, value, waitTime, ttl)`。

### 4.2 已修复：JWT 解析器每个请求重建一次

**现象**：修复 4.1 后重跑，出现 19 个 HTTP 500，响应体不是业务 JSON（断言报 `No results for path: $['code']`）。

**原因**：`JwtUtil.parseToken` / `validateToken` 每次调用都执行 `Jwts.parser().verifyWith(key).build()`。JJWT 的 `build()` 内部要跑一次 `ServiceLoader` 服务查找（`io.jsonwebtoken.impl.lang.Services.loadFirst`），**并发首次初始化时存在竞态**，抛出：

```
java.util.NoSuchElementException
    at io.jsonwebtoken.impl.lang.Services.loadFirst
    at io.jsonwebtoken.impl.DefaultJwtParserBuilder.build
    at org.example.util.JwtUtil.validateToken
```

`JwtParser` 是不可变、线程安全的对象，本该只建一次。

**修复**：改为字段初始化时构建一次，两个方法复用同一个 `parser` 实例。修复后 500 归零（19 → 0）。

### 4.3 已修复：锁释放早于事务提交

**现象**：第 2、3 轮各出现 1 例失败，日志为 `选课失败：并发冲突，课程刚刚已满`（学生 82 号）。候补队列 89 人而不是 90 人。

**原因**：`selectCourse` 是 `@Transactional` 方法，解锁写在方法内的 `finally` 里。**事务是在方法返回之后才提交的**，于是存在这样一个窗口：

1. A 线程释放锁（但事务尚未提交）
2. B 线程拿到锁，读到的课程人数还是旧值（如 9）
3. B 认为还有名额，继续走选课流程
4. B 的原子扣减执行时读到 A 已提交的值（10），`WHERE selected_count < capacity` 不成立 → 影响行数 0 → 抛「课程刚刚已满」

**影响**：本该进入候补队列的学生被报错，候补漏 1 人。**不影响不超卖**（数据库防线依然有效）。

**修复**：两处改动。

1. 把解锁放到事务提交之后执行——用 `TransactionSynchronizationManager.registerSynchronization(...)` 在 `afterCompletion` 回调里解锁，而不是在 `finally` 里，从根上消除「后一个线程读到旧人数」的窗口。
2. 把「原子扣减影响行数为 0」的分支由抛 `BusinessException` 改为转入候补队列。既然防超卖完全由数据库那条原子 SQL 裁决，扣减失败就只说明名额刚被抢完，应当排队而不是报错。

修复后上述症状（学生被报「课程刚刚已满」、候补漏 1 人）不再出现。

**复验**：

| 校验项 | 结果 |
|---|---|
| 请求成功（`code=200`） / 断言失败 | **100 / 0** |
| `selected_count` | **10** |
| 选课记录数（`status=0`） | **10** |
| `course_selection` 总行数 | **10**（没有多出「幽灵选中」记录） |
| 候补队列人数 | **90** |
| **是否超卖** | **否** |

第 2、3 轮那 1 例失败消失、候补从 89 补满到 90，正是本节两处修复的直接效果。总行数 = 10 = 容量这一项，同时验证了「先原子扣减、成功后再写记录」的顺序修复。

> 本轮为单次复验，**不是对照实验**：吞吐 39.0 req/s（平均响应 972 ms）低于第 2、3 轮的 65.3，属本机负载波动（复验前刚重建过容器）。本报告的有效结论是「0 超卖」这条不变量，而非单轮 TPS。

## 五、性能瓶颈分析：为什么调优连接池和日志没有用

第 2、3 轮唯一的差别是配置：Redis 连接池 `max-active` 2→50、日志级别 DEBUG→INFO、MyBatis 关闭 stdout SQL 打印。**结果吞吐完全没变**（65.3 → 63.9 TPS，差异 2%，属于噪声）。

这是一个**结论性的对照实验**：

- 如果瓶颈是 Redis 连接池，把 2 改成 50 应该显著变快 → **没有变化**，排除
- 如果瓶颈是 DEBUG 日志，关掉后应该显著变快 → **没有变化**，排除
- 剩下的唯一解释：**瓶颈是那把粗粒度的分布式锁**

**为什么锁是瓶颈**：100 个请求被锁排成一队，一次只能进一个。每个请求在临界区内要查学生、查课程、查时间冲突、查学分、写选课记录、更新人数，约 10–20ms。于是：

- 100 个请求 × ~15ms ≈ 1.5 秒，**全部串行**
- 平均响应 1071ms 里，绝大部分是**排队等待时间**，不是实际处理时间
- 最后一个请求要等 ~1.5 秒才轮到

**正确的优化方向**：缩小锁的范围，或干脆去掉锁。因为防超卖靠的是 4.1 节那条原子 SQL，锁对「不超卖」并不是必需的——它只是把所有请求串了起来。去掉锁后 100 个请求可以真正并行，理论上吞吐能提升一个数量级。

> 本轮未继续做这项优化，仅完成定位与验证。
